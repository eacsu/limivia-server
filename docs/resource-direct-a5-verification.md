# a5 资源直接确认与 BLE 短测

日期：2026-10-25～26。按本轮要求采用 A 方案：保留资源/实例模型，快速操作直接回复最终状态。SDK、固件均为 **0.3.0a5**，contract 为 **limivia-v3-jsonrpc2-r2**。

## 实现与验证边界

- 固件工作线程继续执行驱动；actor 保留原 RPC 的关联，完成后回复原 ID，等待期间仍能处理心跳和停止。每 endpoint 一个普通待答帧，batch 最多 8 项；实例/停止 epoch 在准入和执行时校验。原生测试覆盖延迟完成、心跳、停止屏障、旧实例、断连释放、原 ID 保真及完成阶段逐个 JSON 分配失败点。
- GPIO open/read/write/status、已有 PWM duty/status 使用直接结果；慢操作继续 accepted/job。回复含资源、实例、修订、设备观察时间和实际状态；GPIO open 另含完整 info。
- SDK 不再每次调用前 resource.get；GPIO.write 返回 GPIOState，PWM.set_duty 返回 PWMState，GPIO.read 仍返回 int。缺失/错配确认结果报告 unknown，不重发写入。显式 jobs.submit 在发送前拒绝快速操作。
- 工作台直接合并 GPIO 确认电平，创建后局部加入资源；移除常规 LED 预检、重复 status 和整板快照等待。SDK 只等在途普通请求/当前页，连续 4 个前台帧后让后台页继续；停止和心跳优先。
- 浏览器用现有 WebSocket operation 终态完成等待，缓存 128 项并核对 generation/boot；漏通知时每秒只读查询任务。
- 连续快速操作导致 snapshot_expired 时，共享查询按本地快速操作版本重启只读分页，保留确认值。高级 batch、GPIO group、RMT sync 和子资源预检也适配实例参数；批量直接结果同步到板图。

## 测量口径

仅环境 A：Linux / BlueZ 5.72 / Bleak 3.0.2，UGREEN `33fa:0012`、`hci1`。BLE 地址 `E4:B0:63:CA:B4:7A`，握手设备 ID `e4:b0:63:ca:b4:78`，板型 `luatos-esp32c3-usb`、bus。环境 B / Windows 本轮未测。

固件诊断确认 ATT MTU **185**、连接间隔 **30ms**，SDK 实际分片容量 **182 字节**。请求继续使用有响应写，234 字节 GPIO 写请求分两片。未切换为无响应写。

无头 Chromium、1440×900，使用真实平台按钮。界面延迟从 DOM click 到“确认标题已更新且下一次操作按钮可用”，由 MutationObserver 记录。它包含浏览器、HTTP、SDK 排队和设备执行回复；不等于独立 ATT 往返，不包含光学或示波器测量。

计时使用隔离的 127.0.0.1:8001 实例。空闲样本在后台分页完成后各点一次；观察场景显式开启后台观察，各点一次。任务开始元数据确认前两次没有在途快照，后两次有在途快照。结束恢复正式 0.0.0.0:8000 实例。

## 对照结果

旧值来自 [同一 Linux 板卡的 a4 流程拆解](led-single-action-profile.md)，是历史单次对照，不作为当前版本的统计分布。

| 操作与负载 | a4 界面耗时 | a5 界面耗时 | a5 前台设备请求 |
|---|---:|---:|---|
| 首次创建并点亮，含首次按需令牌申请 | 2161ms | **202ms** | control.acquire 一次 + resource.open 一次 |
| 已有资源、后台观察中熄灭 | 1731ms / 9 RPC | **169ms** | **1 次 resource.call** |
| 已有资源、空闲熄灭 | 未做本轮匹配对照 | **194ms** | 1 次 resource.call |
| 已有资源、空闲点亮 | 未做本轮匹配对照 | **148ms** | 1 次 resource.call |
| 已有资源、后台观察中点亮 | 未做本轮匹配对照 | **158ms** | 1 次 resource.call |

同边界观察场景熄灭，1731→169ms，单次降低约 **90.2%**；首次创建点亮 2161→202ms。以上均是单次对照。

| a5 样本 | N | 平均 | P50 | 最大 | P95 |
|---|---:|---:|---:|---:|---|
| 空闲界面开关 | 2 | 171ms | 171ms | 194ms | 不估计 |
| 观察开启界面开关 | 2 | 163.5ms | 163.5ms | 169ms | 不估计 |
| 四次已有资源界面操作合计 | 4 | 167.25ms | 163.5ms | 194ms | 不估计 |

样本少，P95/长期成功率没有可靠意义，按用户要求没有延长稳定性测试。

## 功能、失败与剩余问题

隔离计时的 GPIO 创建一次、已有资源写入四次均成功，设备确认的逻辑电平与预期逐次一致；写请求失败 **0/4**、结果未知 **0/4**，创建失败 **0/1**。隔离测试上下文曾完成关闭和重新连接；正式实例最终的 BLE 连接及 LED 原状态恢复尚未完成。没有物理光强/波形测量，不能据此证明其他外设或长期稳定性。

共享 8000 的先行短测另存，已有资源界面操作出现 **379～1002ms** 的较慢样本。该连接/负载与隔离样本不同，没有混入上表，也不能将场景差异全部算成优化收益。所有先行成功 LED 操作同样保留在原始记录中。

冷连接问题仍存在：首个测试镜像曾遗漏头文件中的 r2 握手常量，已修复、重刷，并加入独立字面值版本断言。修正后也出现过连接失败及扫描未发现目标；确认 hci1 没有其他活动连接后复位目标适配器，随后完成共享及隔离实例的 BLE 功能验证。恢复正式实例时再次出现冷连接失败，不能声称连接稳定性问题已经解决。SDK 和后端补充保留具体 GATT 错误，避免被通用提示覆盖。随后记录到明确的“尚未发送业务请求”的 GATT 建连超时，以及 BlueZ 临时 device not found；未把这些错误计为写请求失败。适配器软件复位、重新枚举驱动和目标板控制器复位均未带来可靠恢复，现有证据不足以完全归因于固件、适配器或 BlueZ。

用户表示当前不方便物理插拔适配器后，停止进一步重连。正式服务保持 `0.0.0.0:8000`、hci1、原运行数据目录，当前为 disconnected；未恢复原 GPIO13 高电平。此项明确保留待恢复。

本轮不是连接成功率矩阵；连接准备、扫描失败、握手修正和恢复动作分开记录，不计算没有统一分母的“连接成功率”。未重新测量 USB、独立底层 GATT 分布或完整分页分布，也未将早先 a4/Windows 数据混入 a5 性能统计。固件仍保留会话心跳、消息完整性和停止恢复；没有自动重发任何写操作。
