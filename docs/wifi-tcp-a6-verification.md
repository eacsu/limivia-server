# a6 Wi-Fi 继续定位：TCP、WebSocket 小包发送与双网卡路径

日期：2026-10-26，Linux 环境 A，B47A。用户指出 Wi-Fi 不应停在约 111ms，并明确接受自定义 TCP；沿用「临时固件实验，不改主程序」边界。

## 已验证的结论

- 自定义 TCP 已跑通原 JSON-RPC v3 r2，包括设备握手、会话、GPIO13 写入/状态、单页查询和资源清理，没有改压缩、业务消息或实例确认语义。
- 同一临时镜像、同 boot、同一受控网络条件下，WebSocket 服务端 TCP_NODELAY 从 0 改为 1，GPIO 开关均值 **100.226→48.765ms**；相同业务走 TCP 为 **47.693ms**。两个方案本轮均值接近，不能据此断言自定义 TCP 全面优于 WebSocket。
- 受控轮的主机有线路径中，64 字节原始 TCP 回显 P50 7.539ms、最小 6.324ms、均值 18.331ms。剩余网络仍有波动，约 49ms 不是 Wi-Fi 能力上限，更不能把回显最小值当作 GPIO 写入承诺。
- 包头抓取发现双网卡同网段造成跨接口入站，影响绑定接口的诊断；临时 ARP 隔离后本轮未再捕获此现象。该环境问题和 WS 小包发送策略是两个不同因素，不混为一个根因。
- 已回刷原正式 a6 镜像、恢复 USB 工作台及测试前 GPIO13 高电平；两张网卡的 ARP 参数均恢复原值。正式 server/SDK/固件工作区运行源码未改，实验快照仅在独立分支，本轮不合并、不推送、不发布。

## 受控业务对照

有线主机路径是「主机有线→AP→板卡 Wi-Fi」。顺序：USB1 → WS NODELAY0-1 → TCP1 → WS NODELAY1-1 → WS NODELAY1-2 → TCP2 → WS NODELAY0-2 → USB2。随后独立测量「主机 Wi-Fi→AP→板卡 Wi-Fi」的 WS0/TCP/WS1 各一轮。每轮两次 ping 预热不计时，不自动重发写入。

以下单位 ms，单元格为 N：平均 / P50 / P95 / 最大。P95 最近秩；N=10 时等于最大，短测不代表长期尾延迟。

## 延迟在哪里

主机 API 计时使用同一单调时钟；固件收包/发送使用 MCU 单调微秒时钟，只比较各端内部持续时间，不跨时钟直接相减计算单向延迟。请求数字 ID 用于相关，后台心跳冲突或环形缓冲未保留的条目不强行配对。

下表仅含有完整关联时序的有线主机 GPIO 写入子样本，因此 N 和总均值与前表不同。单位 ms。

| 方式 | N | API 总均值 | 调用→写入 | 写 API | 写入→收到回复 | 回复→返回 | 固件完整收包→开始发送 | 固件发送 API |
|---|---:|---:|---:|---:|---:|---:|---:|
| WebSocket，服务端 NODELAY=0 | 14 | 100.887 | 0.136 | 0.028 | 100.652 | 0.100 | 10.843 | 2.775 |
| WebSocket，服务端 NODELAY=1 | 14 | 45.623 | 0.153 | 0.032 | 45.339 | 0.131 | 11.304 | 3.636 |
| 自定义 TCP JSON+LF，NODELAY=1 | 12 | 54.200 | 0.134 | 0.012 | 53.967 | 0.099 | 10.254 | 2.568 |

固件收包→发送包含 JSON 解析、actor/worker 排队及处理；发送 API 返回只是数据交给 TCP，不等于已上空口。主机写入→回复包含网络、设备和接收调度/解析，不能直接称作纯网络 RTT。观测到的调用前处理和类型化返回合计约 0.24ms，未覆盖全部读取解析 CPU；没有把 100ms 全归给 Python。

### 小包分段的证据

ESP-IDF 6.0.2 的 components/esp_http_server/src/httpd_ws.c 在发送 WS 帧时分别调用 send_fn 发送帧头和正文。测试读回服务端 socket 的 NODELAY=0/1，客户端均开启 NODELAY。关闭 Nagle 的选项语义参考 [tcp(7)](https://www.man7.org/linux/man-pages/man7/tcp.7.html)。Nagle 本身不是一个固定 100ms 的睡眠定时器，额外等待涉及小包缓存、ACK 及实际网络调度。

抓取仅保留 IPv4/TCP 及 ARP 头部，使用 SLL2、snaplen=60，无业务载荷、无 pcap 原文；按相同连接 TCP 序列号将 2/4 字节段与随后连续的大数据段配对，结合发送源码解释为 WS 帧头/正文分段。不是逐条业务 ID 的空口分析。

| 主机接口 / 选项 / 轮次 | 配对数量 | 头/正文间隔平均 / P50 ms |
|---|---:|---|
| enp13s0 / ws_nagle / 1 | 51 | 85.608 / 86.463 |
| enp13s0 / ws_nodelay / 1 | 52 | 6.353 / 1.567 |
| enp13s0 / ws_nodelay / 2 | 52 | 3.686 / 0.966 |
| enp13s0 / ws_nagle / 2 | 50 | 83.032 / 83.875 |
| wlp10s0 / ws_nagle / 1 | 53 | 81.258 / 82.255 |
| wlp10s0 / ws_nodelay / 1 | 53 | 3.248 / 0.000 |

NODELAY=0 时常见 80 多毫秒的头/正文间隔；NODELAY=1 时明显缩短。这与同一受控轮中的业务耗时改善相互印证，支持先调整发送策略而非归咎 JSON 格式。包头时间戳还可能受接收批处理影响，0ms 不代表零空口延迟；有合并或重传时配对也不保证覆盖所有消息。抓包工具报告内核丢包 0，不等于 Wi-Fi 空口零丢包。

## 双网卡路径及失败记录

- 初始无隔离轮捕获到 25 个跨接口入站 TCP 包：目的为有线 IP .24 却从 wlp10s0 进入，或目的为无线 IP .39 却从 enp13s0 进入。样例含发往 .24 的 SYN-ACK 从无线接口到达；绑定指定接口的测试连接因此无法按预定路径完成。
- Linux 默认 arp_ignore=0 允许某接口回答其他接口拥有的本地 IP；跨接口入站本身不等于内核协议错误，也不等于普通未绑定应用必然连接失败。[Linux 内核 ARP 参数说明](https://docs.kernel.org/networking/ip-sysctl.html#arp-ignore-integer)
- 受控轮仅临时将 enp13s0 和 wlp10s0 的 arp_ignore 从 0 改为 1，各接口仅回答自身 IP；重新通过 USB 临时配置板卡 Wi-Fi，使邻居解析重新进行。没有改接口地址、路由、DNS、防火墙或链路启停。受控抓取中跨接口入站计数为 0。
- root 包装脚本在 finally 中恢复两项原值，结果文件记录 before=0、during=1、restored=0，结束再次读取 sysctl 确认。没有把临时网络策略留作用户的永久配置。
- 初始轮还有诊断 TCP 配置/大段时序导出超时；它们单独保留。后续同时缩短诊断导出至最近 12 项、让配置 socket 无接口绑定，故不能把两轮所有失败率变化都归因于 ARP。主要 NODELAY/TCP 结论仅来自后续同一镜像、同 boot 的受控轮。

## 临时实验与正式产品的边界

本轮证明原业务协议可通过 TCP 工作，并定位一个可消除的重要发送等待。原始回显已出现个位数毫秒样本，但网络仍有长尾，固件业务链路也有约 10ms 以上处理/排队。下一步若继续，应分别看网络返回路径和固件排队；不把这轮约 48ms 作为 Wi-Fi 下限。

原来的 WS 首帧会话兼容问题仍只在实验镜像修补；此前发现的 PWM 即时旧值没有在本轮修复或重新验证。正式应用目前仍是原 a6，不宣称 TCP 选项已经可供工作台用户使用。
