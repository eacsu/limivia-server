# Linux BLE 0.3.0a4 实机定位与对照

> 按用户要求已停止长测并收尾。保留配对延迟、压缩对照、GPIO13百次写入回读及28.54分钟持续样本；未完成一小时、最终冷连接矩阵和平台耗时矩阵，不宣称整体稳定性或全部外设功能通过。

## 环境和版本

只统计环境A。Linux 7.0.0-31-generic、BlueZ 5.72、Bleak 3.0.2，UGREEN USB 33fa:0012 / hci1，控制器04:7F:0E:00:66:DA。目标广播LIMIVIA-B47A，BLE地址E4:B0:63:CA:B4:7A，握手设备ID e4:b0:63:ca:b4:78；外置4MB Flash、合宙CORE ESP32-C3 USB板、bus profile。Windows本轮未测，历史Windows样本不混入统计。

SDK与正常固件均为0.3.0a4，业务契约仍为JSON-RPC v3 / limivia-v3-jsonrpc2。SDK原版对照从fa04752归档到临时目录，经PYTHONPATH只在基线子进程导入0.3.0a3；已安装distribution保持a4，两者分别记在JSONL中，没有切换分支或迁移环境。原实机固件0.3.0-dev和新固件均使用ESP-IDF v6.0.2。

正常候选程序源码为固件1526d7a，独立bus构建build/bus-lowlat，二进制与ACL包装均关闭。ELF SHA256为618aa4944403692d81ff27e8ade4bf09452fc207b8ae0557c1b19390ddc91e1c；应用镜像SHA256为d02bccfd4602e48fbb5e9184a1aa9b607457b2f89329a490527cd20e0602ac6e，1172848字节。SDK库代码基线ab3cd25，版本0.3.0a4；工作台运行代码与上一轮状态恢复修复保持一致。

## 结论和修改依据

1. 旧SDK固定20字节分块并逐块response=True。在原固件不变的控制试验中，仅升级SDK后，完整快照平均从7.31秒降到0.68秒。实际MTU为185，正常请求约130～150字节，升级后一次ATT写即可完成；旧版要等待多次约100毫秒的确认。这是主要延迟来源的直接证据。
2. 主机初始连接间隔为50毫秒，HCI边界确认写通常约100毫秒。固件现在等中心设备订阅通知、GATT已可用后，单次提议15～30毫秒间隔、零外设延迟、4秒监督超时。中心实际接受30毫秒；拒绝时继续使用中心参数，不阻塞RPC，不反复协商。诊断区分申请返回码、异步更新结果和实际参数。
3. 固件管理通道容量原来与SDK不匹配。现对齐普通/管理/停止容量1/4/1，为心跳和停止查询保留空间；SDK优先发送这些管理请求，心跳等待预算参考剩余租约。成功通知不再固定等待，保留控制器拥塞退避、整帧截止时间、代次检查与半帧失败中止。
4. 工作台保留具体BLE错误，适配器参数同时用于扫描和连接。初始快照超时后，同一连接的后台完整快照成功且能力已确认，可以恢复ready并清除旧失败；旧连接代次不能覆盖新状态。server没有复制硬件传输实现。

## 分阶段诊断

HCI范围以对应SDK文件中的ATT写调用时间选取，btmon时间原点按首记录的整秒校准。这里只统计固定ATT承载，包含控制器、无线链路和固件，不包含SDK排队；HCI看不到全部链路层重传，不能声称没有空口重传。

|场景|确认写响应数|平均 ms|P50 ms|P95 ms|最大 ms|
|---|---:|---:|---:|---:|---:|
|a3 / 原镜像 / 50ms|5367|106.41|99.70|149.72|250.41|
|a4 / 原镜像 / 50ms|702|98.95|97.02|144.24|198.73|
|a4 / a4 / 30ms|687|58.62|56.32|86.30|117.01|

确认写包数包括业务与SDK管理流量，不能与业务调用数直接相除为固定分片数。a3被取消的最后一次API写没有对应未确认HCI请求，说明API等待阶段与空口失败不能混为一谈。

a4空闲组的SDK排队687次，平均2.67ms、P95 25.54ms；D-Bus WriteValue调用687次，平均58.89ms、P95 86.55ms，无InProgress或取消。SDK请求计时到协议完成或accepted，作业最终完成另行统计。固件自启动至该组结束的队列等待最大371微秒、RPC处理最大13553微秒、响应入队至通知入栈完成最大48724微秒；这是last/max遥测，不虚构逐请求处理P95，也不将通知入栈当作对端确认。

独立GATT只读基线为100/100，平均123.84ms、P50 100.00ms、P95 199.98ms、最大637.07ms；读取Server Supported Features（2b3a），含Bleak/BlueZ调用。按用户要求未再增加优化后的独立GATT只读样本；HCI确认写分布与业务ping不能代替独立只读样本。

## 连接故障与物理断电对照

早期正常a4镜像独立30次扫描发现25次，25次GATT全部失败；精确恢复原应用后仍复现。原应用、独立gatttool、最小NimBLE程序都复现过不能进入ATT的状态，因此不能仅以新旧成功率差异判定SDK或固件回归。

root HCI抓包已取得。初始两次连接均发出LE Read Remote Used Features（0x2016），命令被控制器接受，但没有对应完成事件，没有ACL数据。一例0x3e未建立，一例直到主机取消；USB设备级复位后又记录六次，仍没有远端特性完成事件，包含0x3e、监督超时与主机取消。全部LE事件临时开启亦未恢复。最小BLE5程序三次GATT均失败，没有业务处理参与。最小BLE4候选只构建、未刷入，不能作为对照结论。

用户随后物理拔插UGREEN适配器，同一hci1、同一控制器地址，USB设备号变为009/004。之后特性交换与ATT恢复，但最初五次扫描仅三次发现、两次GATT成功、一次完成SDK握手；另一例GATT成功后握手断开。故物理断电只是恢复手段，没有单凭一次成功宣称稳定。USB runtime_suspended_time为0，未取得自动挂起导致故障的证据；没有持久关闭自动挂起，也没有改内核或重启主机。

旧版50ms/420ms监督参数与新版30ms/4秒参数由HCI及在线诊断双重确认。BlueZ会学习外设提议的参数，后续连接可能一开始就使用已学习值；不能将学习前后的冷连接耗时混算。最初历史成功率、物理插拔后的五次试验与暖夹具重试分别记录；最终独立冷连接矩阵按用户要求未再执行。当前仍需区分主机/控制器特性交换问题与已建立链路上的API等待；未证明只由固件、适配器驱动或距离单方引起。

内核Unexpected continuation: 1 bytes不能独立作根因。[Linux针对Barrot的上游修复](https://kernel.googlesource.com/pub/scm/linux/kernel/git/stable/stable-queue/+/611709b0869e8b0cce2fbfbfc2da00693d27ac2f/queue-6.12/bluetooth-btusb-check-for-unexpected-bytes-when-defr.patch)显示处理多余字节后也可能输出该提示。此处没有以屏蔽日志替代修复。

## 压缩实测及选择

文本和压缩候选均为a4、MTU185、30ms、无观察任务，相同100次ping、100次单页、30次快照和10次完整能力发现，业务调用均成功。

|操作|文本P95 ms|压缩P95 ms|变化|
|---|---:|---:|---|
|ping|91.14|90.94|降低0.2%|
|状态单页|94.16|118.13|增加25.4%|
|完整快照|479.90|539.98|增加12.5%|

这组数据没有达到“分页查询P95至少降低15%，其他主要P95不回退超过5%”的采用门槛。因此正常固件和SDK不启用压缩，未发布新线协议。候选使用512字节DEFLATE窗口、16KiB工作区，已有Python与生产C双向700组向量及CRC、长度、分片、连续帧、解压上限和sanitizer检查；实机已完成上述只读互通，但没有二进制LED、持续测试或跨平台验收，不扩大结论。

## 后台观察、LED与持续测试

a4的acceptance模式在同一真实BLE连接上，每两秒启动一次SDK完整快照观察；前台依次查询、100次GPIO13交替输出与逐次回读，再执行一小时ping/完整快照循环。这是SDK观察负载，不是实际浏览器工作台持续测试；最终平台任务矩阵已取消，没有用SDK数据代替平台耗时。

观察开启时，100次ping、100次单页、30次快照、10次能力发现均成功。100次LED写入与数字回读全部匹配，均等待SDK业务完成；每次计时包含写入、作业完成和读取，不声称是纯GPIO切换延迟或光学/波形测量。SDK关闭资源时，resource.close作业完成后，以resource.get返回resource_not_found判定删除成功；原始失败事件保留，不把这一条预期负查询计作LED业务失败，也不声称所有底层RPC零错误。

持续段按用户要求在1712.50秒（28.54分钟）停止：622次ping、622次完整快照均成功；含前序查询和LED阶段的后台快照共673次，全部成功。持续段没有记录断连、心跳失败、notifications.gap或结果未知。停止后USB只读核对资源为空，admission_rejected=0、tx_failed=0、lost_notifications=0、stale_completions=0；rejected=1对应前述关闭确认的预期负查询。手动停止的SDK取消不算故障，不声称完成一小时或长期稳定性验收。

本轮实机功能覆盖仅限查询、GPIO13板载LED写入与数字回读、资源释放；其他外设没有重新验证。新状态恢复逻辑有回归测试，按用户要求未再进行实机超时注入。

用户要求BLE功能必须通过后，补做了短的真实工作台验收：无头Chromium访问实际8000后端，经BLE点亮LED，GPIO13资源204确认ready、高电平；读取返回1，再由页面熄灭，读取返回0，关闭LED资源后快照为空。刷新页面仍ready、kind=ble、stale=false、snapshot_sync=current，页面异常0。首轮验收脚本误把definition.pins读为顶层pins而停止，错误证据保留；查询确认已点亮后修正脚本继续，未重发点亮。该轮是实际浏览器/HTTP/SDK/固件闭环，没有使用测试后端。证据为hci-root/ble-functional-result.json、ble-functional-attempt1-resource-shape.json及ble-functional.png；这是短功能通过，不是全外设或长期稳定性结论。
