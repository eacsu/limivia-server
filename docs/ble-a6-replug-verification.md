# 0.3.0a6：蓝牙适配器重新插拔后验证

日期：2026-10-26，Linux 环境 A。UGREEN BT6.0、VID:PID `33fa:0012`、hci1，目标 `LIMIVIA-B47A` / `E4:B0:63:CA:B4:7A`，握手设备 ID `e4:b0:63:ca:b4:78`。SDK、固件均为 **0.3.0a6**，契约 `limivia-v3-jsonrpc2-r2`；Python 3.12.3、Bleak 3.0.2、内核 7.0.0-31-generic。

## 结论

插拔后可以建立 BLE 连接，但延迟不稳定，不能认定已经恢复稳定可用。第一条连接的 a6 GPIO 状态查询约 60ms，第二条连接约 714ms；即使保持 MTU 185、连接间隔 30ms，仍有明显退化。a6 对状态查询减少一次确认写的收益已在当前连接上验证，不能把第一条连接的快样本作为长期承诺。没有继续修改协议、SDK、固件或蓝牙参数。

## 测试边界与统计口径

- 保留正式 USB 工作台和原 GPIO13 高电平；BLE SDK 为独立只读连接，不创建、停止或修改资源。USB 会话及心跳仍在，结果属于这个明确负载，不冒称完全空闲链路或工作台 BLE 操作耗时。
- 每条连接内交替使用实际 a6 编码与原命名编码，顺序均为 a6／原编码／原编码／a6。只替换测试进程的编码选择，实际发送仍使用 SDK 的原确认写实现。
- API 延迟从调用开始到类型化设备确认；包含 SDK 排队、确认写、设备执行及通知。确认写的 await 耗时另存 wire；它不是独立 ATT 读往返或空口重传统计。Generic Access 设备名只读特征未提供，本轮没有独立 GATT 读延迟样本，也未做 HCI 抓包。
- 初始一次 SDK 的 5 秒扫描未发现目标，随后一次未过滤扫描发现 B47A（RSSI -40），两次正式 SDK 扫描均发现目标。建连成功率只计算实际发起的连接：**2/2**，不把扫描未发现计入连接尝试，也不据此推断长期成功率。
- 两次建连及 hello 分别约 **4.700s、9.369s**，不含各自约 5 秒扫描。总计 **116 次计时业务调用，非预期失败 0**；分页聚合一次算一次，内部 RPC 数另计。预热、诊断及前后快照不混入该样本数。
- 两条连接独立展示，不合并成一个延迟分布。短测不能证明长期稳定性。P95 采用最近秩；N<10 不报告 P95，N=10 的 P95 等于最大值。

## 能确认和仍未确认的原因

- 实际请求记录中，原格式 GPIO status 为 189～191 字节、两次确认写；a6 为 170～174 字节、一次确认写，单片载荷 182 字节。此 BLE 只读连接没有 control 令牌，因此缩减字节数与 USB 控制会话的 56～59 字节不同。
- 连接 1 的 status 发送 await 平均从约 117ms 降到 56ms，完整调用从 126ms 降到 60ms；ping 两边都是一片，均约 60ms。协议精简的改善范围与分片数相符。
- 重连后，单片确认写也出现约 1 秒等待；旧编码和 a6 都受影响。状态、分页和快照不能统一宣称提速；尤其完整快照第二次连接两种编码均显著变慢。
- 连接 2 的设备诊断确认 MTU 185、连接间隔 30ms，参数更新成功；末次固件排队约 236µs、RPC 处理约 3039µs、通知发送约 2839µs。这些是最后一次处理及累积峰值，不是与每条慢请求一一关联的全链路分解。
- 主机内核仍报 `Bluetooth: hci1: Unexpected continuation: 1 bytes`，包括本轮约 10:15、10:17 的时段；BlueZ 在连接结束附近报 `No matching connection for device`。这证明主机蓝牙链路仍有异常记录，尚不足以认定某条日志就是延迟根因。没有以低 RSSI、协议包长或 CPU 忙作为未经验证的唯一解释。
- 瓶颈目前定位到确认写／返回等待占用明显，固件末次业务处理远小于端到端等待；仍需 HCI 与主机/空口时序关联，才能进一步区分适配器、驱动、链路重传与通知调度。本轮按短测要求停止，不用延长超时掩盖问题。

## 正确性、恢复和现状

- 两次均核对同一设备、a6 版本和 build/boot。前后资源均为 id=138、instance=138 的 GPIO，实际查询仍为 output/high、enabled=true、errors=0。没有写入 GPIO，也没有未知结果重发。
- 未出现非预期断连、心跳失败或请求结果未知。每次测试结束主动断开 BLE；第二次诊断中的 lost_notifications、stale_completions 均为 0，rejected=12 前后未增长，是已有累计值。无空口抓包，不据此保证物理链路零丢包。
- 正式实例仍为 **0.0.0.0:8000，经 USB 连接**，ready、stale=false、snapshot_sync=current，GPIO13 高电平。没有把正式实例切到这条延迟仍波动的 BLE 链路。
- LED 开关与 USB→BLE 切换测试未执行：自动审批以本轮未明确授权 GPIO 输出变化为由拒绝了该步骤，已单独请求具体授权。只读结果不能代替点灯写入或页面按钮延迟结论。
