# 0.3.0a6：USB 协议精简验证

日期：2026-10-26。按用户要求先用有线连接验证，只有收益可复现且没有明确性能或正确性退步的部分才保留。SDK、固件均为 **0.3.0a6**。

## 保留的改动

只读管理查询与 `resource.call/status` 使用固件原已支持的 `[context,args]`，省去重复字段名及查询不使用的 control 字段。session、seq、resource、instance 全部保留；单条发送、batch 预检和队列大小校验使用同一编码函数。

写入、open/close/recover、消费型 read/events、握手、停止和订阅继续使用原命名报文。固定相同 ID、序号和参数时，写报文与原编码相同，测试对此作等价断言。公共 `encode_command` 默认行为保持不变。

契约继续是 `limivia-v3-jsonrpc2-r2`，没有新增压缩算法、二进制协议或指令。固件仅更新版本标识及说明，驱动、BLE 参数和协议解析不变。a5 的两种 r2 参数语法继续兼容。

## 实验与筛选

目标仅为 Linux 主机上的合宙 CORE ESP32-C3 简约版、bus，设备 ID `e4:b0:63:ca:b4:78`。稳定串口 `/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_E4:B0:63:CA:B4:78-if00`。使用项目 Python 3.12、Poetry 环境及同一个 SDK USB 连接；没有使用模拟设备数据作为实机结论。

首先在 a5 固件上比较原编码、所有请求换位置参数、位置参数结合省去只读 control 三种形式，再做反向对照。单独换包络未获得一致收益，第一轮 ping 平均约 6.51→6.91ms，因此不保留。写入也未显示稳定收益，最终只对只读请求采用紧凑形式。

正式验收在刷入 a6 后，用实际 a6 SDK 的 `wire_command_object`，与原 `command_object` 在同一连接交替比较。顺序为 **a6／原编码／原编码／a6**，四段共约 4.4 秒，不含连接准备；每段先做两次状态预热。命名、位置参数均由同一固件处理，消除不同机器、不同连接和固件业务实现的差异。测量使用实际 API 调用前到类型化确认结果返回的耗时，包含 SDK 编码、串口传输、固件处理和返回校验，不等于 USB 总线物理延迟或浏览器点击耗时。

## 正式结果

单位 ms。两组样本数相同；P95 使用最近秩，短样本仅作描述，不能当作长期尾延迟保证。完整快照和发现样本太少，不报告有统计意义的 P95。

| 操作 | 每组 N | 原编码：平均 / P50 / P95 / 最大 | a6：平均 / P50 / P95 / 最大 |
|---|---:|---|---|
| GPIO 写入 | 20 | 12.230 / 12.070 / 12.942 / 13.078 | 12.219 / 12.030 / 13.001 / 13.005 |
| GPIO 状态 | 40 | 11.885 / 11.837 / 12.646 / 16.860 | 11.132 / 11.054 / 11.949 / 12.012 |
| 业务 ping | 40 | 6.459 / 6.188 / 7.076 / 7.135 | 5.835 / 5.997 / 6.101 / 6.302 |
| 单页状态 | 20 | 10.309 / 10.410 / 10.791 / 10.921 | 9.578 / 9.553 / 9.987 / 10.001 |
| 完整快照（6 页） | 6 | 51.207 / 50.812 / — / 53.587 | 49.636 / 49.719 / — / 50.341 |
| 完整能力发现（28 页） | 2 | 353.265 / 353.265 / — / 354.122 | 331.947 / 331.947 / — / 333.683 |

GPIO 状态、ping、单页状态的平均耗时分别降低约 **6.3%、9.7%、7.1%**。能力发现均值少约 21ms，但样本小。写入约 12.2ms，视为持平，不算优化收益；其 P95 的 0.059ms 差异小于前面各基线轮次的波动，未发现可复现的写入回退。后续也不据此承诺写入提速。

### 请求确实变短

以下来自实际发到串口的字节长度，包含 LF。ID、序号位数造成范围差异；不记录令牌值或完整报文。

| 请求 | 原编码 | a6 |
|---|---:|---:|
| GPIO status | 226 字节 | 167～170 字节 |
| session.ping | 172 字节 | 114～116 字节 |
| state（含分页的 revision 参数差异） | 173～188 字节 | 115～132 字节 |
| capabilities | 180～181 字节 | 122～125 字节 |
| GPIO write | 234 字节 | 232～234 字节，仅 ID/seq 位数差异；编码规则未变 |

只读请求约少 56～59 字节。按之前 BLE 的 182 字节载荷估算，本次短 ID 的 status 请求有机会从两片变一片；这只是分片数量推算，**没有实测 a6 BLE 延迟，不能宣称 BLE 性能已经改善**。本轮没有尝试修改 BLE 间隔、确认策略或冷连接恢复。

## 正确性和稳定性口径

- 正式对照包含 **256 次业务 API 调用**（聚合查询一次算一次），非预期失败 **0/256**；没有重发写操作。内部分页的设备 RPC 数不与业务调用数混计。
- 两组共 40 次 GPIO 写入，逐次核对设备返回的实际电平、模式、资源实例、修订和观察时间，全部一致。
- 补充真实 USB 混合 batch：位置参数的 state 与原格式的 GPIO write 一起执行成功。
- 故意使用错误 instance 的写入得到 `stale_instance`，随后实际读取仍为原电平。此预期拒绝单独计数，不当作通信失败。
- 测试资源关闭后完整快照确认资源数为 0。短测没有连接中断、心跳失败或结果未知，不代表长期稳定性。
- 正式工作台用无头 Chromium 完成点亮→熄灭→点亮、刷新恢复，设备确认一致，没有页面异常。最终 USB ready、`stale=false`、`snapshot_sync=current`，GPIO13 高电平，恢复了之前尚未恢复的 LED 状态。
- 没有光学或示波器测量，不把驱动/协议确认当作外部电气精度证明。
