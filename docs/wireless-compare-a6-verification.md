# a6 临时固件：USB、Wi-Fi WebSocket 与 BLE 功能和延迟对照

日期：2026-10-26。用户要求刷写临时固件、保持主程序代码不变，做简单功能及性能对照。本轮仅 Linux 环境 A、B47A，不使用 Windows 或历史 BLE 样本补齐本轮数据。

后续已在同一受控镜像中比较 TCP 与 WS 小包发送：WS NODELAY=0→1 的 GPIO 均值约 100→49ms，自定义 TCP 约 48ms，并识别双网卡跨接口回包。详见 [后续 TCP/WS 定位记录](wifi-tcp-a6-verification.md)。下文保留本轮原始条件与样本，不重写成后续优化结果。

## 结果与交付边界

- USB 最快：GPIO13 高低切换平均 12.592ms；Wi-Fi WebSocket 默认配置 111.490ms；成功连接的 BLE 为 253.348ms。均为 SDK 调用到设备返回的延迟，不是浏览器点击或物理波形延迟。
- 默认三链路对照：USB 2/2、WebSocket 2/2 建连成功，BLE 1/2。BLE 第一次在 GATT 建连阶段超时，未发起本轮业务测试；第二次完成测试。
- GPIO 开关、查询及资源释放正常。PWM 延迟读回正确，但立即返回的确认值有时仍为上一次占空比；不能把本轮称为所有功能正确。
- 发现原固件 WebSocket 初始化与 ESP-IDF 6 握手行为不匹配。先仅在隔离临时镜像中加兼容处理，才完成 Wi-Fi 对照；当前正式固件没有合入这个修补。
- 关闭 Wi-Fi modem sleep 未带来明确改善，额外探测出现 ICMP 重复回复。当前网络结果不代表 Wi-Fi 协议或芯片的性能上限。
- 已回刷测试前完全相同的 a6 应用镜像，恢复原 USB 工作台及 GPIO13 高电平。server、SDK、固件主工作区运行源码均未修改；仅提交验证文档和非活动实验补丁。

## 设备、版本与负载

- 目标：合宙 CORE ESP32-C3 简约版、外置 4MB/DIO/40MHz，设备 ID `e4:b0:63:ca:b4:78`，BLE `E4:B0:63:CA:B4:7A`，USB 使用已确认的 by-id 路径。没有操作 BDD6。
- SDK 0.3.0a6，来源 `540d7fa`；固件基于 `2bb2c2c`，ESP-IDF 6.0.2、bus、契约 `limivia-v3-jsonrpc2-r2`。临时构建启用已有 `LV_BLE_TRACE=ON`，增加不含载荷的 WS 元数据和会话初始化兼容处理。
- 默认对照的 build ID `adebdcb08c0bac164f5198d9404a00e998dc17dc337051387b9b1735ab659d6b`，boot ID `add8028e54f951b8`。每次连接均核对设备、build 和 boot。
- 正式后端测试期间断开设备，不运行工作台后台观察。每轮只有一个活跃业务 SDK 会话；全部默认对照均保持板卡 Wi-Fi 已连接，所以 BLE 是 Wi-Fi/BLE 共存场景，不与此前 Wi-Fi 未启用的 BLE 样本混用。
- 网络：板卡获配 `192.168.1.40`；实际路由为主机 `enp13s0/192.168.1.24 → AP → 板卡 Wi-Fi`。主机同时有 `wlp10s0/192.168.1.39` 连接同网段。本轮不是主机仅使用 Wi-Fi 的双无线端场景，也没有改主机路由或断开其网络接口。
- 用户明确授权读取当前 NetworkManager 配置用于临时配网。密码经内存管道传入测试进程，未写入固件、日志或实验 JSON；配置 persist=false，Wi-Fi 驱动存储模式为 RAM。回刷后确认 Wi-Fi 未启动、未连接。

## 默认三链路对照

顺序为 USB1 → WS1 → BLE1 → WS2 → USB2 → BLE2；每轮两次 ping 预热不计时。相同 GPIO/PWM 操作仅使用板载 D5/GPIO13；PWM 为 1000Hz、10bit，依次设置 10/25/50/25/0%。每轮创建后再操作，结束确认资源数为 0，显式释放协议控制令牌。

## 功能问题：需要与性能分开处理

### WebSocket 初始化

原处理函数依赖 HTTP_GET 握手调用来分配 ws_fd、路由 generation 和 sess_ctx。ESP-IDF 6.0.2 的 components/esp_http_server/src/httpd_uri.c:362 明确在完成 WS 握手后直接返回，不调用普通 URI handler。实际元数据为 ws_calls=1、ws_upgrades=0、ws_slot=0：升级成功，第一条 TEXT 到达时却没有会话，固件立即关闭连接。

临时兼容处理在首帧发现 sess_ctx 为空时分配槽位并继续处理当前帧，没有更改业务协议或 SDK。其后 WS 两次默认轮和两次 no-sleep 轮均完成握手与功能测试。实验补丁仅保存于 [WS 临时补丁](experiments/wireless-a6/ws-idf6-temporary.patch)，不是已生效的主程序修复。no-sleep 的增量补丁见 [省电实验补丁](experiments/wireless-a6/wifi-no-sleep-temporary.patch)。

### PWM 即时确认旧值

现有实现 ledc_update_duty 后立即 ledc_get_duty，读到的值有时尚未更新。独立 USB 复核中：请求 25%，立即回复仍约 9.971%；20ms 后读回约 24.927%；请求 50% 时立即回复仍约 24.927%，随后读回约 49.951%。这是与链路无关的即时确认正确性问题，不将它归因于 BLE。

默认阶段即时旧值：USB 6/10、WS 6/10、BLE 3/5，共 15/25；关闭省电阶段 WS 8/10。总计 23/35 次 PWM 立即确认与请求不符。所有 35 次在等待 20ms 后查询的占空比都与请求一致，容差 0.2 个百分点；该容差覆盖 10bit 量化，不代表示波器测得精度。PWM 驱动 errors=0。

表中的 pwm_duty 仅表示设置 API 返回，不能作为新占空比已经确认的延迟。pwm_readback_confirmed 包含人为的 20ms 等待和一次 status 请求，35 次均确认成功；它不与即时 GPIO 写入延迟混称同一指标。本轮不修改正式 PWM 实现。

## 网络层探测与限制

- 在 WIFI_PS_NONE 镜像上额外发送 5 个 ICMP Echo：5 个唯一回复，另外出现 2 个重复回复；ping 报告 0% 唯一请求丢失，RTT min/avg/max 为 49.443/108.972/160.733ms，其中均值包含重复回复。
- 同一时段 TCP 建连 N=5，平均 34.715ms、P50 9.471ms、最大 136.274ms。未把 TCP 建连当成业务请求耗时。
- 网络本身已有延迟及重复包线索，不能将 WS 的约 100ms 全归为 MCU 执行、SDK 编码或协议固有上限。尚未区分 AP、无线时序、主机双网卡同网段及其他路径因素；没有进行 TCP/空口抓包，不作确定根因结论。
- 当前仅短测、小消息和简单 GPIO/PWM，没有持续吞吐、长时间稳定性、物理波形测量或跨机器可靠性结论。BLE 的单次成功不能替代失败的建连样本。

## 测试准备失败与恢复

准备脚本曾因变量覆盖导致预期的 HTTP 断开未发出；后续 esptool 复位使原 USB 连接失效。应用分区读取与原镜像逐字节比较一致后才继续写入，随后显式断开后端残留连接。另一次准备在已建 SDK 会话中同步等待凭据输入，阻塞心跳，触发 session_changed/结果未知；只读复核确认同 boot、Wi-Fi 未初始化后，将凭据读取移到建立会话之前，再进行配网。这些准备错误单独留档，不算作传输性能样本。

最初的功能轮暴露 PWM 即时旧值并触发断言，也与最终计时样本分开保留；没有删掉失败尝试后宣称所有功能正确。

测试结束仅回写应用分区 0x20000，esptool 校验成功，未改分区表、NVS、文件系统或 eFuse。原镜像与板上备份均为 1175296 字节，SHA256 `00289d6467a9346c6dc24936e61506ba1c323bd355a952a5eb4625f8d49b49a5`。正式原 build ID 恢复为 `57e9d89a3486768d4fa32c1f025890de3e93845d8495f0d0c41d94f67c0a702a`。

正式实例仍监听 0.0.0.0:8000，USB ready、stale=false、snapshot_sync=current，恢复一份 GPIO13 高电平资源。无头 Chromium 确认页面已连接、LED 显示已点亮且控制按钮可用，没有 pageerror；恢复后的 wifi.status 确认 started/initialized/connected 均为 false。
